## Map: a new List stopped waiting for the old map; t-SNE / UMAP / PCA layouts (branch `feature/map-projections`)

- Reported: *Map the List only* on 3,000 tracks, then a 100-track playlist: the new map came only after minutes.
  Cause: `_remap` during a load set `_again` but never `_stop`, so the old t-SNE ran all 750 steps, its result was
  thrown away, and only then the new List was mapped (`set_store` already stopped it). Fix: `_remap` sets `_stop`;
  t-SNE checks it every step. Test: a fake slow first load that runs until told to stop (fails without the fix).
- Asked: other projections, chosen by the user (seen in robertolupi/deep-cuts: Rust UMAP over CLAP + text vectors,
  PCA as the alternative). *Layout* box below the map: t-SNE (default), UMAP, PCA; setting `Map projection`.
  - numpy only (the spec excludes scipy and numba): `umap_layout` = exact kNN (15, in row blocks), UMAP's fuzzy
    graph, PCA init, umap-learn's optimiser with each epoch's edge updates applied at once (vectorized).
    `pca_layout` = randomized SVD with fixed signs (no mirrored map after a re-compute).
  - Cache: t-SNE under the model id as before (old caches stay valid), UMAP under `<model>:umap`; PCA not cached.
- Benchmark on a copy of the real LAION cache (3,411 tracks; kNN10 kept / Spearman rho of pair distances / time),
  3,000 tracks: t-SNE 35 % / 0.50 / 142 s, our UMAP 22 % / 0.56 / 5.6 s, umap-learn 24 % / 0.54 / 21 s, PCA
  7 % / 0.60 / instant. 100 tracks: t-SNE 53 %, UMAP 57 % (umap-learn 57 %), PCA 34 %. So the numpy UMAP matches
  the reference; t-SNE keeps more neighbours on big maps, UMAP and PCA more of the large-scale structure.
- Not released (user's decision): to be tried from source on the user's own machine first.
