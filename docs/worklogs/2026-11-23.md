## GPU failure mid-analysis: fall back to the CPU instead of failing every track

Came out of a chat about ONNX Runtime providers ("is it slow because it uses my CPU?", then "is picking the fastest
provider enough?"). Reading `OnnxEmbedder` for that answer showed the fallback only covered *creating* the session.

- **Bug:** if the GPU failed during `session.run` (DirectML device removed after a driver reset, out of memory), each
  `embed()` raised, `run_analysis` saved an error for the track, and stored errors are only cleared on a cache schema
  bump. So one GPU reset marked every remaining track of the run failed, until their files changed.
- **Fix** (`core/embeddings.py`): `OnnxEmbedder.embed` catches a non-CPU failure and redoes the track on a fresh CPU
  session. CPU works: the GPU was the problem, the embedder stays on the CPU for the rest of the run (`gpu_failure`
  says why), the next start tries the GPU again. CPU fails too: the track is the problem, its error is raised and
  the GPU session is kept, so one odd file cannot move a whole library onto the CPU. `Cancelled` is not a failure.
- `run_analysis` sends a new `('device', provider, message, worker)` event when a model moves; the UI
  (`ui/embedding_worker.py`) shows *CPU* in the status and emits one warning even if both processes report it.
- **Tests:** `tests/test_gpu_fallback.py` (6): the embedder switch, a bad track keeps the GPU, stop is not a failure,
  CPU errors unchanged, the UI event, and a `run_analysis` run where the GPU breaks after track 1. That last one
  fails on the old code with `['analysed', 'failed', 'failed', 'failed']` and passes now with four `analysed`.
  Full suite 372 passed; the real-model test (`SONGSELECTOR_CNN14_ONNX=dist/models/cnn14.onnx`) passes on DirectML.
- **Not done (from the same review, ranked):** measure GPU vs CPU speed and agreement once per machine (extend
  `tune()`), a user setting to force the CPU, the local log file (BACKLOG Diagnostics) so a report of "analysis is
  slow" shows which device was used.
