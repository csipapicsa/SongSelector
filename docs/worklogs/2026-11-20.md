## Mixxx library (branch `feature/mixxx-library`)

Why: Mixxx is the DJ program Linux users have; the Linux build needs it as a source like Traktor on Windows.

- User installed Mixxx 2.5.6 in WSL (PPA `ppa:mixxx/mixxx`; Ubuntu's own package is 2.3.2), library
  `/mnt/e/DJ/BREAKBEAT_ANALYZED` (374 tracks), two playlists, ratings and colours.
- What Mixxx stored (decoded from the database): keys and BPM of 372 tracks came from the file tags (Traktor's
  Open Key text `9d`, integer BPM; the key blob's `source` = 1 = FILE_METADATA in Mixxx's `src/proto/keys.proto`).
  The beatgrid of a tag-only track is a placeholder (first beat at frame 0); only tracks loaded into a deck or
  re-analysed got Mixxx's own analysis (`qm-tempotracker`, decimal BPM; one halved: 68.1 for a 136 track).
  SongSelector needs BPM and key, not the grid.
- Schema facts checked against the real database and Mixxx's source: `library.key_id` is ChromaticKey (1-12 major
  from C, 13-24 minor), `rating` 0-5, `color` 0xRRGGBB or NULL, `Playlists.hidden` 0 playlist / 1 Auto DJ /
  2 history; `~/.mixxx` on Linux.
- User decisions: (1) **primary DJ program wins**, others fill gaps; (2) **exact colours** on screen, colour
  families for search. Also: the app's own rating/colour should go later (BACKLOG TODO); own BPM analysis
  (study Mixxx) is an optional later idea (BACKLOG).
- Implementation: `core/mixxx_library.py` (TraktorCollection's shape, reads a copy), `core/dj_programs.py`
  (priority), `core/track_colors.py` (family number or `#RRGGBB`; hue bands checked against Mixxx's, Rekordbox's
  and Traktor's palettes from Mixxx's `predefinedcolorpalettes.cpp`), sync per program (`mixxx_seen` table;
  `fill_only` for the non-deciding program; a library read before the primary's waits for it so the result does
  not depend on read order), *Import -> Link Mixxx library...* and *Primary DJ program*, *Mixxx Playlists* in the
  Browser (playlists, Crates, History newest first), selfcheck reads a small Mixxx library inside the exe.
- Behaviour change: at a program's first sync, no colour there no longer clears the tags' colour (it made the
  result depend on which program was read first).
- Real data: the branch's reader on the user's WSL library: 374 tracks, both playlists + history, 7 ratings,
  5 colours in the expected families.

- First WSL test (user): playlists appear. Added "Import missing tracks" to the List's bar for another program's
  playlist (it was only in the Browser's right-click menu). WSL set-up: the 7 model files copied from `dist\models`
  (checksums OK); `wslview` registered for folders so *Open models folder* opens Explorer.

## Research: int8 models (PR #45)

- `docs/research/experiments/quantization/benchmark_int8.py`: fp32 vs int8 (onnxruntime dynamic quantization), CPU,
  DirectML and CUDA, 10 tracks, plus the percentages the app shows for 12 prompts. Result: slower everywhere and
  broken (the spectrogram front-end got quantized; description-search % off by 17 points on average). Not worth it
  on the GPU (no kernels for dynamic quantization); a fair CPU test is open. CUDA fp32 was oddly slower than
  DirectML in the test environment (not investigated).
- Explained to the user: dynamic vs static PTQ vs QAT; why int8 usually works (error averaging, flat minima,
  normalisation); how quality was measured (fidelity to fp32: window cosine, kept neighbours, app percentages).
- User observation: CNN14 separates DnB from house/downtempo better than LAION on the map. Explained (AudioSet genre
  labels and rhythm vs caption-trained general audio); the Windows app's map was on Microsoft CLAP. Backlog: model
  choice for the map, similarity measures for CNN14.
