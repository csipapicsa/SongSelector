## 2. Benchmark: CNN14 on the CPU, PyTorch vs compiled vs onnxruntime (test only)

Question (chat): is a model faster on the CPU when it runs as C/C++ instead of Python? Wanted as a
test on ~10 random tracks, not in the app.

The app already does this: CNN14 was exported from PyTorch to `cnn14.onnx` and runs in
onnxruntime (C++). The original PyTorch pipeline still exists (MusicFindBoundaries venv, torch
2.5.1 + panns_inference), so both can be measured on the same audio.

- `tests/test_inference_speed.py` (skipped unless `TKC_CNN14_ONNX`, `TKC_TORCH_PYTHON`,
  `TKC_BENCH_TRACKS` are set): picks random tracks from a folder or a `library.sqlite` (read-only),
  decodes them once with the app's `load_audio`, and runs the same chunks through four backends,
  each in its own process with the same threads and one chunk per call. Asserts identical
  embeddings (< 1e-3 from PyTorch) and prints a table.
- `tests/benchmarks/cnn14_backends.py`: standalone worker, also runs under the torch venv.

Result (seed 648823, 10 tracks, 60.8 min of audio, 4 threads):

| backend | load s | model s/track | vs PyTorch | max diff |
|---|---|---|---|---|
| PyTorch eager | 6.9 | 10.54 | 1.00x | 0 |
| TorchScript (traced, frozen) | 6.7 | 7.99 | 1.32x | 5.2e-06 |
| onnxruntime, no graph optimisation | 1.1 | 7.26 | 1.45x | 2.0e-05 |
| onnxruntime (as the app) | 1.0 | 7.09 | 1.49x | 2.0e-05 |

Decoding took 8.7 s for all 10. So: yes, ~1.5x on the CPU, and the app already uses the fastest
option. Most of it comes from leaving Python's per-layer dispatch (TorchScript alone gets 1.32x);
onnxruntime's graph optimisations add ~2 %. The convolutions themselves were always C++ in both.
The GPU (0.58 s/track) remains ~12x faster than the best CPU option. One run, backends one after
another; per-track times vary by ~20 %.

## 3. Browser tab: saved playlists and smartlists; ordered Playlist with # (4.21.0)

Request (chat, screenshots of the app's playlist and of Traktor's browser): the left pane gets two
tabs, the Playlist and a Traktor-like view with *Track Collection* and *Playlists*. Playlists can
be saved, loaded and dragged into the List view; smartlists save the Complex Search settings
(not the search bar); playlists are ordered, so a **#** column. Answers to my questions: dragging
a playlist or smartlist into the List loads its tracks there; no folders under Playlists for now;
Traktor / Rekordbox playlists later (BACKLOG); smartlists store only Complex Search rows.
Background: the ordered playlist is meant to feed a next-track predictor later (DJ mix
segmentation project), so the order is always stored.

- **Storage** (`library_store.py`, schema 3): `saved_lists` (name unique ignoring case, kind,
  smartlist rules as JSON) and `saved_list_tracks` (ordered path keys, a track once per
  playlist). Separate from the internal `lists` table, so a user list called "Playlist" or
  "Library" cannot collide with the panels' own lists. `tracks(keys)` lets the Playlist tab keep
  tracks that are no longer in the library list when it saves.
- **# column** (`config.POSITION_COLUMN`): appended to `HEADER_LABELS`, shown first; not a track
  field (`FIELD_LABELS`), so it is not searchable, not in Complex Search, not on the map. Playlist
  tab: renumbered on every save. List: the position while a saved playlist is shown, else empty.
  Writing it switches sorting off for the loop: while sorted by #, Qt re-sorted after each
  change, skipping rows (and would be slow on 3,651 rows).
- **Browser** (`ui/list_browser.py`): a QTreeWidget of nodes `{'kind', 'name'}`; artist/album/
  genre folders fill when opened (1,682 artists: 0.01 s). Emits clicked / double-clicked /
  tracks-dropped / menu; the window does the rest (`ui/saved_lists.py`, a mixin, to keep
  `main_window.py` from growing further).
- **List shows an entry**: `filter_items` also asks `_in_source`; playlist = its path keys,
  smartlist = its active rules through the same matcher as Complex Search (`_matches_rules`),
  collection = exact column text. Shown in 0.2-0.3 s on the real library.
- **Drag and drop**: track drags also carry `application/x-songselector-tracks` (all selected
  paths, also missing files); Browser entries `application/x-songselector-node`. Hovering a drag
  over a tab opens it (`setChangeCurrentOnDrag`), so a playlist can be dragged from the Browser
  to the Playlist tab. Drops from Explorer still import as before.
- Found on the real data: with *Hide playlist tracks* on, a saved copy of the Playlist tab
  showed 0 tracks in the List. A shown saved playlist now ignores that option.

Verification: 159 tests + 192 table subtests (2 skipped: need the real model / benchmark setup);
12 new tests (store, Browser entries, # order and restart, moving and inserting rows, dragging
entries to the List and Playlist tab, tracks onto a Browser playlist, smartlist edit / rename /
delete, name clashes, Save as Smartlist). Screenshots of the app on a copy of the real library

path set).
