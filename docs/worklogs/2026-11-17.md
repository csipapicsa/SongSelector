# 2026-11-17

## Plan for 1.2.0

The user's feedback list after using 1.1.4 (map, playlist, duplicates, cover art, freezes) goes into the same
release as the unreleased 1.1.4. New features, so **1.2.0** (SemVer minor); one release instead of two. Plan and
order in `docs/BACKLOG.md` ("Release 1.2.0"): A map follows the List, B map interaction, F tag edits without
freezing, E busy indicator, C playlist selection on the map, G delete duplicates three ways, D map in its own
window, H cover art. User decisions: button name "Map the List only"; duplicates keep the row whose file exists,
then the richest row, then the one in the Traktor / Rekordbox collection, then the first; cover art from the file
and from `cover.jpg` / `folder.jpg`.

## A. The map follows the List (branch `fix/map-follows-list`)

User report: after a new description search (or switching LAION / Microsoft CLAP, which searches again) the map
showed only part of the new List, a mix of the old and the new search; pressing *Only listed tracks* did not
bring the new tracks.

- Cause: `set_only_listed` stored `frozenset(self.listed)` in `SimilarityMapWidget.only` when the button was
  pressed, by design (a snapshot; the old test said "a snapshot: the list moved on"). `build_map_data` loads only
  those keys, and `set_tracks` shows only listed keys: the map showed old snapshot ∩ new List.
- Fix: while the mode is on, `set_tracks` (re)starts a 300 ms single-shot timer; `_follow_list` takes the List as
  it is then and re-maps, unless the map already shows exactly these tracks. A change during a running load sets
  `_again`, so the load that ends next is followed by one for the latest List. Button renamed *Map the List only*;
  status says "only the tracks the List shows"; edge tooltips explain that "to the N most similar" is per track.
- Tests (written first; all fail on the old code, checked by swapping in the old `similarity_map.py`): a new
  description search maps exactly the new List; a burst of four filter changes gives one `build_map_data` call;
  a change during a load ends with the latest List; re-filtering to the same rows or moving the tempo maps
  nothing again. The old snapshot test now expects the map to follow.
- Full suite: 229 passed, 3 skipped; ruff (src, tests) clean.

## B. Map interaction (branch `feature/map-interaction`, on top of A)

- **Esc in two steps:** `deselect()` first calls the new `end_compare()` when a track is compared (Ctrl+click or
  a clicked match), keeping the selection; the second Esc clears the selection as before.
- **Ctrl+click on empty space** ends the comparison: `MapView.mousePressEvent` checks for a `DotItem` under the
  mouse (edges and glows are items too, so "any item" would not do). Ctrl+click on the compared dot already ended it.
- **No overlapping boxes:** new `core/placement.py` (no Qt, unit-tested): `place_box` tries four corners around
  the anchor in a preferred order and takes the first that covers none of the boxes placed before and stays in
  the viewport; otherwise the least covered. `SimilarityMapWidget._layout_boxes` places the label (prefers above),
  then the compare card, then the hover card (prefer below), in viewport pixels, with the three dots themselves
  counted as taken. Label and cards got `box_size()` / `set_corner()` (new `MapLabel` class; `label_text` kept).
  Runs on select, compare, hover, zoom (wheel, fit), resize and 3D rotation: the boxes have a fixed pixel size,
  so whether they collide depends on the zoom.
- **Closest matches dropdown:** `match_filter` (*all* / *harmonic only* / *Edges selection*) replaces the
  `harmonic_only` checkbox. Edges selection reuses `core.similarity.connection` (the same rule the edges use).
  Tracks without a key stay when a mix type is checked (as with harmonic only); colour and rating can rule them
  out. Changing the Edges menu rebuilds the list in this mode. Setting `Map match filter`; the old
  `Map harmonic only` is read once and removed.
- README map table: Ctrl+click, Esc, the dropdown, *Map the List only*.
- Tests: placement unit tests (corners, overlap, order, three boxes at one point, screen edge, no free corner);
  GUI: Edges selection follows the menu, old setting carries over, Ctrl+click on empty space, label and two cards
  zoomed far out do not overlap; Esc test now two steps. The three behaviour tests fail on A's map code (the two
  cards overlapped by ~74,000 px²). Full suite 239 passed, 3 skipped; ruff clean.

## F. Tag edits without freezing (branch `fix/edit-without-freeze`)

User report: editing Artist / Title froze the app for ~10 s.

- **Measured first** (`cProfile` on a copy of the real library, 3,389 tracks, and a copy of one MP3; the real files
  were not touched). On C: (NVMe) one edit took 0.6 s, so the guess "the file write is slow" was wrong. With the
  data on E: (where the library and the music live: a DRAM-less SATA SSD, Crucial BX500) 2.5 s idle and 4.3-5.5 s
  with a helper process reading audio and committing small SQLite writes (like the analysis). 75-90 % of it was
  `_save_library` -> `save_list`: upsert of all 3,389 rows plus delete / re-insert of the list order, for one
  changed track. The real analysis loads disk and CPU more, so ~10 s is plausible.
- **Fix:**
  - `ui/background.py` `BackgroundWriter`: one worker thread, jobs in submit order (two edits of one file cannot
    overtake each other), result or exception delivered on the UI thread through a queued Qt signal; `busy_changed`
    (for the spinner, block E), `flush()` for closing and tests. `closeEvent` flushes before closing.
  - `edit_track_tags`: the job reads the fingerprint, writes the tags and refreshes the fingerprints; the callback
    re-reads the file, merges the row and submits `upsert_tracks([record])` (one row; the list order is unchanged).
    Status "Saving ... to file..." until done; errors in the status line and the same warning dialog as before.
    A track removed from the library while its file was written is not added back.
  - **Found on the way:** only CNN14's fingerprint was refreshed after a tag-only edit, so LAION and Microsoft
    CLAP re-analysed every edited track. Now every model whose embedding was current (`EmbeddingStore.fingerprint`,
    one row instead of all fingerprints) keeps it.
  - *Edit track info*: the path is selectable (mouse and keyboard).
- **Result**, same setup (E:, under load): the call returns in ~1 ms, the longest UI pause (10 ms timer) is under
  100 ms, the edit is done in 0.1-0.35 s.
- Tests: `test_background.py` (order, threads, errors to on_error / `failed`, busy signal, flush timeout); tag
  edits: does not block (slow write patched in), only the changed row is saved (`save_list` must not run), every
  model's fingerprint kept, two quick edits end with the second, a removed track is not added back, path
  selectable. Four of them fail on the old window code (one, the ordering test, passes there too: it guards the
  new asynchronous code). Existing edit tests wait for the worker.
- Not in this PR (backlog F2): imports, removal and dedupe still save the whole library on the UI thread.

## E. Busy spinner (branch `feature/busy-spinner`)

- `ui/busy_spinner.py` `BusySpinner`: a painted 270° arc turning at 20 fps. Reference-counted by reason
  (`set_busy('Saving to the file', on)`), so overlapping work (a save during a search) keeps it turning until the
  last reason ends; the tooltip lists the reasons. Idle: hidden and the `QTimer` stopped (no CPU). Fixed size, so it
  cannot widen the window (the 1.1.3 stretch bug).
- Wired in: status bar left of the status text (`BackgroundWriter.busy_changed`; description search from
  `describe()` until results or failure), left of the analysis progress (while a track is analysed or tracks are
  missing; off when paused or failed, also for a late progress event after pausing), and the map's status line
  (arranging: `load` / `_loaded`; grouping: from "Grouping..." until the latest request's result, off when
  grouping is switched off). Model download was in the plan, but its dialog already has a progress bar: left out.
- Tests: spinner unit tests (idle hidden and timer stopped, several reasons, tooltip, painting); window: tag edit,
  description search (stand-in engine), failure, analysis progress / pause; map: arranging and grouping.
- Debugging note: the new window test first killed the test process silently (exit 127). Cause: the stand-in
  search engine had no `stop()`, which `closeEvent` calls; PyQt5 aborts the process on an exception raised in a Qt
  override. The test stub now has `stop()`.
- Full suite 255 passed, 3 skipped; ruff clean.

## C. Playlist selection on the map (branch `feature/playlist-on-map`)

- `MainWindow._highlight_playlist_selection` (Playlist `itemSelectionChanged`, and on every map refresh) sends the
  selected Playlist rows' fields to `SimilarityMapWidget.set_highlighted`.
- Map: `highlighted` tracks get an amber ring (`PLAYLIST_RING`). Those the List does not show (`_markers`) are added
  to `fields` (so they are drawn, hoverable, selectable), with a dashed ring and a paler fill, and are excluded from
  closest-match candidates and from edges (unless selected), so the List's results do not change. Selecting a
  marker shows its closest matches among the listed tracks.
- *Map the List only* maps contain only listed tracks: `MapData.place` adds a highlighted track without a new
  layout. Its vector is centred with the map's own centre (`MapData.centre`, kept by `build_map_data`; new
  `similarity.raw_vectors` / `centred_unit`, `track_vectors(..., with_centre=True)`), and its 2D / 3D positions come
  from `place_new` (similarity-weighted average of its most similar mapped tracks). One embedding is read with
  `store.load(key)` instead of loading the store. After a re-map the highlighted tracks are placed again.
- Status line: "k of n selected Playlist tracks shown"; an unanalysed one counts as not shown.
- The plan's "field lookup by a dict" was not needed: the selection's fields are read from the selected rows only.
- Tests: `MapData.place` (same vector space: nearest tracks of the own style; position closer to the own style's
  centre; already mapped keys skipped); window: amber ring and its removal, filtered-out track shown but not
  matched / no edges and its own matches from the List, placement on a *Map the List only* map and after a re-map,
  unanalysed track reported. (A first version of the placement test asserted the 5 nearest *dots*: too strict for
  an 18-point t-SNE; it now tests what `place` guarantees.) Full suite 260 passed, 3 skipped; ruff clean.

## F2. Save only what changed (branch `perf/save-changed-rows`)

User question: does rewriting the whole database wear the SSD? Answer: a save writes about the file's size (7.7 MB);
a 1 TB BX500 is rated ~360 TBW, i.e. tens of millions of such saves: wear is not the problem, the latency is. Fixed
anyway, which also writes less.

- `LibraryStore`:
  - upsert `... DO UPDATE SET ... WHERE (columns) IS NOT (excluded.columns)`: an unchanged track is not written
    (before, `updated_at` changed on every row, so every page was rewritten).
  - `save_list` diffs the stored `(position, path_key)` with the new list: deletes / writes only the positions
    that changed; an unchanged list writes nothing.
  - `journal_mode=WAL`, `synchronous=NORMAL` (as the embedding caches). Connections are opened per call, so the WAL
    is checkpointed and removed when each closes: still a single `library.sqlite` between saves.
- Measured on a copy of the real library on E: with the disk-load helper: a save after one change **0.13 s**
  (was 2.5-5.5 s).
- Imports still took ~2 s: profiling showed `populate_tree` (rebuild and re-sort of all 3,400 rows) dominating,
  not the database. New `_add_or_update_rows` (imports of up to 200 tracks: new rows added, existing redrawn, one
  sort) and `_remove_rows` (*Remove from library*), both followed by `_list_view_changed` (browser, # positions,
  group colours, filter). One-file import **0.65 s**; the rest is sorting / filtering the QTreeWidget (backlog:
  model-based view).
- Tests: unchanged save leaves the file's mtime and no `-wal` file; only the changed track gets a new `updated_at`;
  list order through append / remove / reorder / reverse / empty / one; incremental import and removal produce
  exactly the rows of a full rebuild (with `populate_tree` patched to fail). Four fail on main's code (the order
  test passes there too: it guards the diff). Full suite 265 passed, 3 skipped; ruff clean.

## G. Delete duplicates, three ways (branch `feature/smart-duplicates`)

- `core/duplicates.py` (no Qt): `find_duplicates(table, mode, in_collection, exists, size, digest)` -> `[Group(keep,
  remove, reasons)]`. Modes: `PATH` (canonical path), `ARTIST_TITLE` (casefolded, whitespace collapsed; rows
  without artist or title are never grouped), `SAME_FILE` (group by size, SHA-256 only where sizes collide, the same
  path hashed once). Keep rule (user, 2026-11-17): file exists > richness (filled `RICH_FIELDS`, colour / rating 0
  count as empty) > in the Traktor collection or on a Rekordbox playlist > first. `reasons` feed the preview.
- `ui/duplicates_dialog.py`: groups as tree items, the kept row bold, removable rows checkable; the OK button
  counts the ticked rows.
- Window: the menu entry is a submenu with the three modes, each with a preview. "Same file" runs on the
  `BackgroundWriter` (reads files) with the spinner. Collection membership is a set of path_keys made on the UI
  thread (`TraktorCollection.keys()`, Rekordbox playlist tree), so the worker touches no shared state. The rows are
  those of a snapshot: if the List changed before the user confirmed, nothing is removed ("run it again").
  `delete_duplicate_tracks()` without arguments still removes same-path duplicates without a dialog (selfcheck).
- Tests: keep rule (exists / richness / collection / first, reasons), `filled`, artist-title normalisation, path
  mode, same file (copies found; only same-size files hashed), dialog (untick keeps, button text / disabled); window:
  preview shown and confirmed, cancel removes nothing, artist-title keeps the richer row and persists, same file in
  the background with the spinner, list changed meanwhile. (One test first expected 2 artist-title removals: the
  fixture's second "one" is titled "one again", so 1 was right.) Full suite 276 passed, 3 skipped; ruff clean.

## D. Map in its own window (branch `feature/map-window`)

- `ui/map_window.py`: `MapWindow` (top-level `QWidget`, no parent: own taskbar entry, free placement on another
  screen; geometry saved as base64 in the settings) and `MapPlaceholder` (the tab meanwhile: bring the window to the
  front / show the map here again).
- The map's checkable *Own window* button emits `detach_requested`; `MainWindow.set_map_detached` swaps the tab
  (signals blocked so the swap does not refresh the map half-way), reparents the widget, keeps the button's state and
  text in sync, saves `Map detached`, and refreshes the map. `map_visible()` is true while the window is visible, so
  the map keeps following the List. Closing the window docks the map (`closed` signal); closing the app closes the
  window without docking, so it opens detached next time. Ctrl+2 (`show_map`) raises the window or shows the tab.
- Tests: detach and dock (placeholder, follows the List, button / setting in sync), geometry remembered, detached
  state restored on restart, Ctrl+2. Full suite 279 passed, 3 skipped; ruff clean.
