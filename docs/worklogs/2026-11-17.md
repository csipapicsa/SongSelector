## A. The map follows the List (branch `fix/map-follows-list`)

User report: after a new description search (or switching LAION / Microsoft CLAP, which searches again) the map
showed only part of the new List, a mix of the old and the new search; pressing *Only listed tracks* did not
bring the new tracks.

- Cause: `set_only_listed` stored `frozenset(self.listed)` in `SimilarityMapWidget.only` when the button was
  pressed, by design (a snapshot; the old test said "a snapshot: the list moved on"). `build_map_data` loads only
  those keys, and `set_tracks` shows only listed keys: the map showed old snapshot ∩ new List.
- Fix: while the mode is on, `set_tracks` (re)starts a 300 ms single-shot timer; `_follow_list` takes the List as
  it is then and re-maps, unless the map already shows exactly these tracks. A change during a running load sets
  `_again`, so the load that ends next is followed by one for the latest List. Button renamed *Map the List only*;
  status says "only the tracks the List shows"; edge tooltips explain that "to the N most similar" is per track.
- Tests (written first; all fail on the old code, checked by swapping in the old `similarity_map.py`): a new
  description search maps exactly the new List; a burst of four filter changes gives one `build_map_data` call;
  a change during a load ends with the latest List; re-filtering to the same rows or moving the tempo maps
  nothing again. The old snapshot test now expects the map to follow.
- Full suite: 229 passed, 3 skipped; ruff (src, tests) clean.

## B. Map interaction (branch `feature/map-interaction`, on top of A)

- **Esc in two steps:** `deselect()` first calls the new `end_compare()` when a track is compared (Ctrl+click or
  a clicked match), keeping the selection; the second Esc clears the selection as before.
- **Ctrl+click on empty space** ends the comparison: `MapView.mousePressEvent` checks for a `DotItem` under the
  mouse (edges and glows are items too, so "any item" would not do). Ctrl+click on the compared dot already ended it.
- **No overlapping boxes:** new `core/placement.py` (no Qt, unit-tested): `place_box` tries four corners around
  the anchor in a preferred order and takes the first that covers none of the boxes placed before and stays in
  the viewport; otherwise the least covered. `SimilarityMapWidget._layout_boxes` places the label (prefers above),
  then the compare card, then the hover card (prefer below), in viewport pixels, with the three dots themselves
  counted as taken. Label and cards got `box_size()` / `set_corner()` (new `MapLabel` class; `label_text` kept).
  Runs on select, compare, hover, zoom (wheel, fit), resize and 3D rotation: the boxes have a fixed pixel size,
  so whether they collide depends on the zoom.
- **Closest matches dropdown:** `match_filter` (*all* / *harmonic only* / *Edges selection*) replaces the
  `harmonic_only` checkbox. Edges selection reuses `core.similarity.connection` (the same rule the edges use).
  Tracks without a key stay when a mix type is checked (as with harmonic only); colour and rating can rule them
  out. Changing the Edges menu rebuilds the list in this mode. Setting `Map match filter`; the old
  `Map harmonic only` is read once and removed.
- README map table: Ctrl+click, Esc, the dropdown, *Map the List only*.
- Tests: placement unit tests (corners, overlap, order, three boxes at one point, screen edge, no free corner);
  GUI: Edges selection follows the menu, old setting carries over, Ctrl+click on empty space, label and two cards
  zoomed far out do not overlap; Esc test now two steps. The three behaviour tests fail on A's map code (the two
  cards overlapped by ~74,000 px²). Full suite 239 passed, 3 skipped; ruff clean.

## F. Tag edits without freezing (branch `fix/edit-without-freeze`)

User report: editing Artist / Title froze the app for ~10 s.

- **Measured first** (`cProfile` on a copy of the real library, 3,389 tracks, and a copy of one MP3; the real files
  were not touched). On C: (NVMe) one edit took 0.6 s, so the guess "the file write is slow" was wrong. With the
  data on E: (where the library and the music live: a DRAM-less SATA SSD, Crucial BX500) 2.5 s idle and 4.3-5.5 s
  with a helper process reading audio and committing small SQLite writes (like the analysis). 75-90 % of it was
  `_save_library` -> `save_list`: upsert of all 3,389 rows plus delete / re-insert of the list order, for one
  changed track. The real analysis loads disk and CPU more, so ~10 s is plausible.
- **Fix:**
  - `ui/background.py` `BackgroundWriter`: one worker thread, jobs in submit order (two edits of one file cannot
    overtake each other), result or exception delivered on the UI thread through a queued Qt signal; `busy_changed`
    (for the spinner, block E), `flush()` for closing and tests. `closeEvent` flushes before closing.
  - `edit_track_tags`: the job reads the fingerprint, writes the tags and refreshes the fingerprints; the callback
    re-reads the file, merges the row and submits `upsert_tracks([record])` (one row; the list order is unchanged).
    Status "Saving ... to file..." until done; errors in the status line and the same warning dialog as before.
    A track removed from the library while its file was written is not added back.
  - **Found on the way:** only CNN14's fingerprint was refreshed after a tag-only edit, so LAION and Microsoft
    CLAP re-analysed every edited track. Now every model whose embedding was current (`EmbeddingStore.fingerprint`,
    one row instead of all fingerprints) keeps it.
  - *Edit track info*: the path is selectable (mouse and keyboard).
- **Result**, same setup (E:, under load): the call returns in ~1 ms, the longest UI pause (10 ms timer) is under
  100 ms, the edit is done in 0.1-0.35 s.
- Tests: `test_background.py` (order, threads, errors to on_error / `failed`, busy signal, flush timeout); tag
  edits: does not block (slow write patched in), only the changed row is saved (`save_list` must not run), every
  model's fingerprint kept, two quick edits end with the second, a removed track is not added back, path
  selectable. Four of them fail on the old window code (one, the ordering test, passes there too: it guards the
  new asynchronous code). Existing edit tests wait for the worker.
- Not in this PR (backlog F2): imports, removal and dedupe still save the whole library on the UI thread.
