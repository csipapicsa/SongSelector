## Match on the map and in Advanced Search; G jump sharp with a sign (branch `feature/match-sizes-search-and-g-jump-signs`)

User asked for three things:

1. **Similarity map, 2D view: dot size follows the Match** while a *Describe a sound* search is shown (cosine
   similarity, -100 % to 100 %).
2. **Advanced Search: Match as a criterion.**
3. **G jump sharp gets a sign**: +3 when the move goes up three, -3 when it goes down.

Asked before coding (3): the move is three semitones, but on the Camelot wheel the same move goes the other way
(8A → 5A is Am → Cm: pitch +3, wheel -3). User chose **the pitch**: +3 = three semitones up.

Done:

- `core/harmonic.py`: `g_jump_sharp` split into `g_jump_sharp_up` (*+3 G jump sharp*, wheel step 9) and
  `g_jump_sharp_down` (*-3 G jump sharp*, wheel step 3), both weight 2, special, same teal edge colour (like +1 / -1
  mix share one). `RENAMED` + `current_names()` turn a saved `g_jump_sharp` (the map's `Map edges` setting) into both,
  so a user who had it ticked keeps both directions. `compatible_keys` now returns both targets; before, the two
  targets shared one dict key and one was lost.
- Map dot size (`ui/similarity_map.py`): `match_scales()` maps the Match of the dots shown to a scale of 0.6–2.2 ×
  `DOT_SIZE`, **relative to the shown range**, not to -100..100 %: CLAP scores sit in a narrow band (often 10–40 %),
  so the absolute scale would draw every dot nearly the same size. **Area** grows evenly with the score (diameter with
  the square root), since the eye compares dots by area. All equal / one score: normal size. The scale multiplies the
  3D depth scale, so it works in 3D too. Bigger dots sit slightly below smaller ones in their ring tier
  (`SMALL_ON_TOP`), so a big dot never hides a small one. The label and cards keep clear of a big dot (`dot_gap`, per
  box `gap` instead of the fixed `DOT_SIZE`). The status line names the range ("dot size: Match, 35 % (smallest) to
  41 % (largest)"). The Match comes from the List's Match column text ('31%'), which the map already receives.
- Advanced Search: `Match` added to `COMPLEX_SEARCH_COLUMNS` and `NUMERIC_COLUMNS`; the row offers only the number
  comparisons for it, with a percent hint. **A Match rule lets rows without a Match value through**
  (`matches_condition`): without that, *Match ≥ 30* with no description search would have emptied the List, and a
  smartlist with a Match rule (smartlists never carry scores) would always be empty.

Tests: harmonic (signs both ways, wrap-around, the way back has the other sign, legacy name), numeric search (Match
comparisons, empty Match passes, dialog row), saved lists (whole window: Match rule filters description results, then
nothing hidden after clearing), map (dot sizes follow the Match, z-order, label gap, back to normal; `match_scales`
area; a saved `g_jump_sharp` edge ticks both). User docs: search, describe, similarity map, key-and-tempo table;
CHANGELOG.

Open: none known. Merged as PR #90. The user looked at it in the app (from source on the live `dist\` data) and
said "good", with the follow-up below.

Also asked: why "+3 G jump sharp" and not "+ G jump sharp"? The 3 never changes for this move, so only the sign
carries information; I followed the "+1 mix" pattern and the user's own "-3". User chose the rename: the labels are
now *+ G jump sharp* and *- G jump sharp* (branch `feature/g-jump-sharp-sign-only`, before the 1.6.0 release so the
released labels don't change later). Internal names (`g_jump_sharp_up` / `_down`) and saved settings are unchanged.

Standing preference saved to memory: previews run the source checkout on the live `dist\` data (settings, library,
embeddings), with a backup first and only while no SongSelector exe is running.

## Advanced Search: an Active tick per rule, equally wide condition boxes (branch `feature/advanced-search-active-tick`)

User asked (with a screenshot of the dialog):

1. **An "Active" tick before every rule**, to switch a rule off and on, instead of setting its column to *None*.
2. **All condition boxes the same width.** The Match row's box was narrower than the rest.

Done:

- `AdvancedSearchRow.active_check` (*Active*, ticked by default); `get_filter()` saves `'active'`. *None* is no longer
  in the column list. `active_filters()` skips unticked rules; a rule saved before the tick counts as ticked. Rows saved
  with the *None* column still don't filter, also in smartlists, which apply their saved rules without the dialog. In
  the dialog they come back unticked, on the first column: which column they had was never saved. An unticked row is
  not validated, so a half-typed number doesn't block OK (as with *None* before).
- Width: the condition box was sized to its own items (`AdjustToContents`), and Match offers only the short number
  comparisons. `ConditionCombo` adds the difference to the widest condition of any column to Qt's size hint, so every
  row's box is equally wide under any style or font. Measuring once in `__init__` would miss the theme's style, which
  is applied when the dialog is shown.
- Checked by eye: offscreen screenshot with the Dark theme (`QT_QPA_FONTDIR=C:\Windows\Fonts`, else offscreen draws no
  text), rows like the user's: all condition boxes 113 px.

The user's live settings hold three rules saved with *None* and an active *Match greater than 50* rule. The released
1.5.0 doesn't know Match (the rule hides every track there) and ignores the tick. Until the next release, untick
*Enable Complex Search* before going back to the exe.

Tests: unticked rule kept and restored with its column, condition and an invalid number; old *None* rows come back
unticked; `active_filters` with ticked, unticked, saved-before-the-tick, *None* and empty rules; equal box widths with
Match, Genre, Speed change, Rating and Artist rows. User docs (search) and CHANGELOG.
