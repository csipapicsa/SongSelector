## Distillation Phase 2: model structure (branch `research/distill-structure`)

User: start the next training step from the backlog; model structure (temporal modelling instead of the time average,
128 mel bands) first, then the relational loss with the best epoch chosen on validation top-10 overlap.

Why structure: after the 4 conv blocks a frame stands for 160 ms and sees ~0.46 s (about one beat), and the student
then averages over time, so it is a "bag of beats": the order of beats, bars and phrases is lost, while the teacher (a
transformer) relates the whole 10 s window. The learning-rate schedule (11-25) showed the neighbour gap is not
optimisation.

Three runs, one change each from the current recipe (`cnn4-small-64-n1199-cosine`: 40 epochs, cosine schedule, seed 0;
test top-10 overlap 0.222, seed range 0.005):

- `cnn4-small-64-tcn`: 4 residual, dilated (1, 2, 4, 8), depthwise-separable temporal blocks after the CNN: each frame
  sees ~5.3 s (two to three bars). +69 k parameters (0.23 → 0.30 M).
- `cnn4-small-64-attn`: attentive statistics pooling (Okabe et al. 2018, ECAPA-TDNN) instead of the plain mean/std.
  +17 k parameters.
- `cnn4-small-128`: 128 mel bands instead of 64, same network (+256 parameters; the cost is CPU time).

Done:

- `students.py`: `TemporalBlock`, `AttentiveStats`; `Cnn4(temporal=, pooling=)`. Both new parts start at zero
  ("zero-init residual"), so at initialisation each new student computes exactly its plain twin (checked: max
  difference 0 and 2e-7); the ReLU sits before the zero-scaled BatchNorm, since a ReLU after it would get no gradient.
  The plain student's state dict is unchanged (an 11-25 checkpoint loads strictly). ONNX vs PyTorch cosine 1.000000
  for all, also with the new layers' weights randomised (an all-zero check would not exercise them); attentive
  pooling checked directly (equal weights = mean/std; peaked weights pick the frame).
- `prepare_data.py --mels N`: `mel<N>.npy` for the cached windows, row for row; each track is also run through the
  64-band front end and compared with `mel64.npy` (stops at the first mismatch). The 128-band cache is 9.0 GB (35,200
  windows × 128 × 1001 × 2 bytes): a git-ignored training cache, not part of the shipped model (~1 MB ONNX that
  computes its own log-mels). Built in 23 min (alongside the first training run), all 3,380 tracks; the 64-band check
  matched `mel64.npy` exactly (max difference 0.0), so every row is the same audio as before.
- `train.py`: reads the cache matching the student; validation top-10 overlap logged per epoch (watched only; the
  best epoch is still chosen on validation cosine, so the runs compare with E02). Smoke run (50 tracks, 2 epochs,
  experiment `distill-smoke`) end to end in 44 s.
- Runs started (logs in `.research_cache/distill/logs/2026-11-26_*.log`).

## Codec robustness: original vs a 64 kbps MP3 copy (same branch)

User: free training sets are often low quality; does audio quality matter for the mel input and the training? A small
test, original vs 64 kbps only, in MLflow. Reasoning before measuring: everything is resampled to 24 kHz (nothing above
12 kHz survives) and the mel stops at 11 kHz, so a codec's treble cut-off above that is invisible; in distillation the
teacher labels the same degraded audio, so a bad copy gets no wrong label. Open: does the teacher itself drift, and
does the log (which magnifies quiet detail) make the student drift more?

- `codec_robustness.py`: 100 test tracks (seeded), each re-encoded to MP3 at 64 kbps CBR with libmp3lame through PyAV
  (no ffmpeg CLI here; PyAV is the app's FFmpeg fallback), copies on D: (`D:\SongSelector-research\codec\64k\<row>.mp3`,
  no track names). Checked on one track first: the app's decoder removes the encoder delay (same length, lag 0), so
  the same windows hold the same moments; every track's lag is measured too.
- Teacher on the CPU (the GPU is training) and two students (`cnn4-small-64-n1199-cosine`, the E02 recipe, and the new
  `cnn4-small-64-tcn-n1199-cosine`) embed the 6 sampled windows of both versions. Per model: window/track cosine
  original vs copy, top-10 stability among the 1,272 test tracks, whether the copy finds its own original first, the
  cosine to the 10th neighbour as the scale; per student the fidelity to the teacher on each version; per mel band the
  copy's log-mel difference. MLflow experiment `distill-robustness`, JSON in `research/results/`.
- Test-set sources: 1,236 MP3, 32 FLAC, 4 WAV (the probed one was 320 kbps), so 64 kbps is mostly a transcode, as a
  low-quality download would be.
- Fixed on the way: a source MP3 with a damaged frame made PyAV raise (the app's mpg123 resyncs); damaged frames are
  now skipped (the copy gets shorter, the length check leaves it out). A WAV with an unnamed "2 channels" layout made
  LAME refuse to open; the encoder now always asks for mono/stereo at an MPEG rate. 25 of the 98 sampled tracks have an
  exact duplicate in the test pool (the copied folder): a copy that finds the duplicate had been counted as a miss
  (teacher "finds itself" 0.86); duplicates now count as the track itself and are no one's neighbours (0.96). The
  first MLflow run is renamed `codec-64k-n98-superseded`.

Results (98 tracks, 2 left out: copy a few ms longer; every copy aligned to the sample; sources median 259 kbps):

| Original vs 64 kbps copy | Track cosine | Finds itself first | Top-10 neighbours kept | 10th neighbour's cosine | Agreement with teacher (orig → copy) |
|---|---|---|---|---|---|
| Teacher | 0.982 | 0.96 | 0.64 | 0.925 | |
| Student, plain (`cnn4-small-64`, cosine recipe) | 0.948 | 0.54 | 0.31 | 0.963 | 0.855 → 0.815 |
| Student, temporal (`cnn4-small-64-tcn`) | 0.975 | 0.78 | 0.51 | 0.964 | 0.859 → 0.839 |

- Where the codec acts (log-mel, copy minus original): below 4 kHz 0.2 natural-log units on average (≈ 0.9 dB, noise
  level); from ~5 kHz it falls away: 7.6 kHz −7 dB, 9.2 kHz −14 dB, 10.5 kHz −23 dB. LAME at 64 kbps low-passes inside
  our 11 kHz mel range, so 64 kbps is not invisible (a typical 128+ kbps cut-off above 12 kHz would be; not measured).
- The teacher still knows the track (96 % find themselves first) but a third of its top 10 changes: neighbours 5-15
  are near-ties (10th at 0.925), so a drift of 0.018 reshuffles the edge of the list. Low bitrates are a mild problem
  for the method itself, not only for the student.
- The students drift more than the teacher (plain 2.9x, temporal 1.4x) and their spaces are denser (10th neighbour at
  0.96), so the same drift moves more neighbours. Trained only on the library's 256-320 kbps audio, they agree less
  with the teacher on the copies (−0.04 plain, −0.02 temporal).
- The temporal student is clearly more robust than the plain one (finds itself 78 % vs 54 %, keeps 51 % vs 31 % of
  its neighbours). Hypothesis, not tested: with context over time it leans more on rhythm and structure, which a
  low-pass does not change, and less on treble texture.
- For training data: the teacher labels copies consistently, so low-bitrate clips are not wrong labels; but a
  student only ever trained on high-quality audio is not robust to low-quality input. Codec copies as augmentation
  (the teacher re-labels each copy) is an option; check FMA's bitrates before the pilot.
- Discussed: the user's point that a shared conversion makes every input "equally wrong" holds above 12 kHz (the
  24 kHz resampling), not for 64 kbps, whose damage starts near 5 kHz; a student trained on degraded input copies the
  teacher's view of degraded audio (which already keeps only 64 % of its top 10).
- **Closed (user):** only wanted to know how quality contributes; DJs play good-quality files, so no follow-up
  (no codec augmentation, no low-pass student). Noted in the distill README ("Side check") and the backlog.
